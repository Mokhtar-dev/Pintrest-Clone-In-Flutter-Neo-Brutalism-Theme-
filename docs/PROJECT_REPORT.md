## 4. How Everything Works (Feature Walkthrough)

### 4.1 Authentication flow
1. App starts → `Firebase.initializeApp` → `AuthGate`.
2. `AuthGate` listens to `FirebaseAuth.instance.authStateChanges()` (persists session across restarts automatically).
3. **Register:** validates handle/email/password → checks `users` for a duplicate handle → `createUserWithEmailAndPassword` → writes `users/{uid}` profile doc with zeroed counters → returns to root.
4. **Login:** `signInWithEmailAndPassword` → `AuthGate` swaps to `HomeScreen`.
5. **Forgot password:** dialog → `sendPasswordResetEmail`.
6. **Logout:** Profile → “more” sheet → “TERMINATE SESSION” → `signOut()` → `AuthGate` swaps back to `LoginScreen` automatically. No manual navigation anywhere — the gate is the single source of truth.
7. Errors are mapped to terminal copy (e.g. `ACCESS DENIED // INVALID CREDENTIALS`) in `AuthService.friendlyError`.

### 4.2 Upload pipeline
```
Home (+) → AddImageScreen → device gallery (image_picker)
        → UploadScreen (title + preview + PUBLISH)
        → Firebase Storage: pins/{uid}/{timestamp}.jpg
        → Firestore: pins/{doc}  (author snapshot, aspectRatio, counters=0)
        → users/{uid}.pinsCount += 1
        → back to feed (live stream shows it instantly)
```

### 4.3 Engagement loop (like / save / comment / follow)
- **Like** → `pins/{id}/likes/{myUid}` created + `likesCount+1` + notification `LIKE` to author (never to yourself).
- **Save (vault)** → `users/{me}/saved/{pinId}` snapshot + `pins/{id}/savedBy/{me}` + `savesCount+1` + author `savesReceived+1` + notification `SAVE`.
- **Save to board** → same as above, plus `users/{me}/boards/{boardId}` gets the `pinId` (`arrayUnion`), `pinCount+1`, first image becomes the board cover; notification target shows the board name (exactly like the designed notification element).
- **Comment** → `pins/{id}/comments/{doc}` + `commentsCount+1` + notification `COMMENT` with the text preview.
- **Follow** → `users/{target}/followers/{me}` + `users/{me}/following/{target}` + both counters + notification `FOLLOW`.

### 4.4 Notifications
- Stored per recipient: `users/{recipientUid}/notifications/{doc}` with `type, actorId, actorName, actorUsername, actorAvatarUrl, pinId, pinTitle, commentText, read, createdAt`.
- The screen streams them newest-first (limit 60); unread items get the lime border + pink pulse dot from the original design; `timeAgo()` renders “2M AGO”.
- The home bell badge appears **only when unread > 0** (live count stream).
- MARK ALL READ batch-updates every unread doc.

### 4.5 Profile & boards
- Stats: `pinsCount` (incremented on upload, decremented on delete), `boardsCount`, `savesReceived` (total saves other users made on your pins).
- SAVED tab = `users/{uid}/saved` (denormalized pin snapshots → instant render, tap re-fetches the live pin).
- Boards tab = `users/{uid}/boards`; Board detail batches `whereIn` (30 per query) to fetch member pins.

### 4.6 Explore
- Client-side search over the live pin stream (title, category, category label, author handle, tags) + the same category pills as Home. Fully styled like the rest of the app.

### 4.7 Demo seeding
- On Home first load, `PinService.seedSamplePinsIfEmpty()` checks `pins` — if empty, it batch-writes the **4 original showcase drops** (SYSTEM MATRIX 04, MERCURY SPHERE, MONOLITH BUNKER 9, FLORA OVERLAY 09) with the same images, badges, badge colors, save counts, tags, a seeded press comment, and matching aspect ratios. Result: a fresh Firebase project renders **exactly like the original mock design**.

## 5. Firestore & Storage Data Model

### Collections

```
users/{uid}
  name, username, email, bio, pronouns, website, avatarUrl
  pinsCount, boardsCount, savesReceived, followersCount, followingCount
  createdAt

users/{uid}/saved/{pinId}            → denormalized Pin snapshot + savedAt
users/{uid}/boards/{boardId}         → name, coverImageUrl, pinCount, pinIds[], createdAt
users/{uid}/followers/{followerId}   → followedAt
users/{uid}/following/{followedId}   → followedAt
users/{uid}/notifications/{notifId}  → type, actor*, pinId, pinTitle, commentText, read, createdAt

pins/{pinId}
  title, description, imageUrl, storagePath, aspectRatio
  category, categoryLabel, tags[], badge, badgeColor
  authorId, authorName, authorUsername, authorAvatarUrl
  likesCount, savesCount, commentsCount, createdAt

pins/{pinId}/likes/{uid}             → likedAt
pins/{pinId}/savedBy/{uid}           → savedAt   (dedupe for counters)
pins/{pinId}/comments/{commentId}    → text, authorId, authorName, authorAvatarUrl, createdAt
```

### Storage layout

```
avatars/{uid}.jpg          (profile pictures)
pins/{uid}/{timestamp}.jpg (pin images)
```

### Security rules (included in the repo)
- `firestore.rules`: signed-in users read pins/profiles; only owners write profiles, boards, saved vaults and notifications; likes/follows keyed so only the actor can create/delete their own docs; only the author can delete a pin or comment.
- `storage.rules`: public read; writes only to your own `avatars/{uid}.jpg` or `pins/{uid}/...` with 5/10 MB limits and `image/*` content-type checks.

**Deploy them (required!):**
```bash
cd pintrest_clone_in_flutter_neo_brutalism_theme
firebase deploy --only firestore:rules,storage
```
If your Firebase project still has the temporary “test mode” rules that expire after 30 days, deploying these is what keeps the app working long term.

## 6. Architecture Explanation

The codebase keeps the existing feature-first structure and adds a thin, explicit data layer (no code generation, no DI framework — everything is a singleton service, which keeps the course-level project approachable):

```
lib/
├── main.dart                      # Firebase init + AuthGate
├── firebase_options.dart          # untouched (FlutterFire generated)
├── core/
│   └── utils/formatters.dart      # counts + relative time
├── services/                      # ← data layer (new)
│   ├── auth_service.dart
│   ├── user_service.dart
│   ├── pin_service.dart
│   ├── notification_service.dart
│   └── board_service.dart
└── features/pinboard/
    ├── domain/entities/           # AppUser, Pin, Comment, AppNotification, Board
    └── presentation/
        ├── screens/               # 13 screens (2 new)
        └── widgets/               # PinCard, Neo feedback kit, legacy widgets
```

- **State management:** screens use `StatefulWidget` + `StreamBuilder` on Firestore snapshot streams. This gives *real-time UI for free* (likes/comment counts update live on every screen) with zero boilerplate. `flutter_bloc` remains in `pubspec.yaml` untouched, but services + streams were chosen deliberately for reliability and readability in this scope.
- **Models:** plain Dart classes with `fromMap`/`fromDoc`/`toMap` — no code-gen needed, easy to read in a report/demo.
- **Errors:** every user-facing action reports through `showNeoTip()` (styled SnackBar) so failures never look broken visually.

## 7. Design Preservation Notes

The instruction “don’t change the design” was treated strictly:

- **No color, spacing, typography, border, radius, icon, or copy of any existing element was changed.**
- Logic replaced mock text in the same widgets (e.g. the profile name widget now renders the real user, but with identical style `w900 / 18px / letterSpacing 0.5`).
- The home feed card was **extracted 1:1** into `PinCard`; the only behavioral states added are: heart turns pink when liked, bookmark icon fills when saved, feed images show a lime spinner while loading (in the same dark card).
- New surfaces that were unavoidable for functionality (bottom sheets, dialogs, Explore screen, board detail) reuse the exact same design tokens: `#0F1110` background, `#161A18` panels, `#B6FF00` accents, `white24` borders, `w900` uppercase labels.
- Empty/loading states reuse the original “SYSTEM MODULE INITIALIZING...” placeholder pattern via `NeoEmptyState`.

## 9. Known Scope Notes / Honest Limitations

1. **Apple/Google buttons** are kept for design fidelity but show “OAUTH UPLINK NOT CONFIGURED” — OAuth requires `google_sign_in`/`sign_in_with_apple` setup (SHA fingerprints, Apple developer account) which is outside this task.
2. **REMIX / RAW SVG / decorative badges** (STAFF SPARK, VIEWING LIVE, ARCHDIGEST.DESIGN) remain styled placeholders by design; they show honest “locked/queued” tips when tapped.
3. **Deleting a pin** removes the document + Storage file and decrements the counter; deeply nested orphan docs (likes/comments of a deleted pin) are left for simplicity — Cloud Functions/`deleteField` cleanup would be the production answer.
4. **Boards are private** to the owner in the rules (matches the “SECRET VAULT” copy in the design).
5. `dashboard_screen.dart` remains unused as it was before; it duplicates Home and was left untouched rather than deleted to avoid removing anything the course might reference.
6. Seeded showcase pins are attributed to a fictional `PIN/DROP ARCHIVE` profile, so your own stats stay accurate.
